## 1. Задание

Разработать MVP веб-приложения — интерактивного тренажёра безопасных сделок для
классифайда.

Пользователь выбирает роль (покупатель или продавец), проходит симуляцию диалога
с контрагентом, принимает решения в спорных моментах сделки, видит последствия
своего выбора и получает объяснение, какие признаки риска присутствовали в
сценарии. По итогам прохождения пользователь получает мотивирующую оценку и
видит свой прогресс между попытками.

**Цель продукта:** пользователь должен перенести опыт тренировки в реальные
сделки — то есть научиться распознавать тревожные признаки *до* совершения
рискованного действия.

**Ключевое ограничение из кейса:** это не «чат с вопросами» и не викторина.
Объяснение должно обучать, а не сообщать «правильно / неправильно».

## 2. Границы MVP

### Входит в MVP

- Прохождение сценариев за роль покупателя и за роль продавца.
- Ветвление диалога в зависимости от выбора пользователя.
- Обучающая обратная связь на каждом шаге и итоговый разбор.
- Балльная оценка и уровень безопасности по итогам прохождения.
- История попыток и динамика результата при повторном прохождении.
- Заранее подготовленный набор сценариев, поставляемый как данные.

### Дополнительный функционал

Реализуется после того, как основной путь работает end-to-end. Полный перечень —
в разделе 7.

- Справочник признаков мошенничества (FR28, FR29).
- Статистика по распознанным и пропускаемым признакам (FR26).
- Продолжение прерванной тренировки (FR12).
- Лучший результат по сценарию на витрине (FR7).

### Не входит в MVP (осознанно)

- Реальная интеграция с классифайдом, чатами и объявлениями Авито.
- Админ-панель для редактирования сценариев через UI — сценарии поставляются
  как версионируемые JSON-файлы и загружаются при инициализации БД.
- Интеграция с LLM для генерации персонального разбора. Решение принято в пользу
  детерминированного разбора: он воспроизводим, не имеет внешних зависимостей и
  не может отказать во время демонстрации. См. раздел 15.
- Мультиязычность, мобильные приложения, офлайн-режим.
- Асинхронные механики: очереди, фоновые задачи, вебсокеты, рассылки.
- Ролевая модель администраторов и разграничение прав внутри команды.

### Продуктовые решения, зафиксированные командой

| Решение | Обоснование |
|---|---|
| Идентификация — регистрация по нику и паролю (FR1–FR3) | Прогресс между попытками — обязательное требование кейса, а значит нужна устойчивая личность. Полноценный OAuth избыточен для MVP. |
| Гостевой доступ к витрине без прохождения (FR4) | Жюри и новый пользователь видят содержание продукта до регистрации, но прогресс требует учётной записи. |
| Сценарии — данные, а не код (FR30–FR32) | Позволяет параллельно писать контент и движок, легко масштабируется на реальные данные, обеспечивает воспроизводимость. |
| Ветвление, а не линейный опрос (FR10) | Требование кейса «показывает последствия выбора»: последствие должно менять ход диалога, иначе это викторина. |
| Все операции синхронные | Принцип KISS, обозримость поведения, простота отладки в команде из четырёх человек. |
| Пять сценариев: по два на роль плюс демонстрационный | Два уровня сложности на каждую роль показывают разные группы пользователей, при этом витрина остаётся простым списком без фильтров и пагинации. |
| Ровно три варианта на каждом шаге: безопасный, спорный, опасный | Компонент диалога пишется один раз под фиксированную сетку; шкала баллов становится единой для всего контента. |
| Шкала баллов из трёх значений: +10 / 0 / −10 | Исключает несопоставимость оценок между сценариями и делает пороги уровней универсальными. |
| Динамика — сравнение с предыдущей попыткой, не график | Отвечает на вопрос «стал ли я лучше» прямее, чем временной ряд, и не требует библиотеки графиков и обработки вырожденных случаев. |
| Четыре экрана: главная, прохождение, результат, справочник | Прогресс встроен в главную страницу, отдельного раздела профиля нет. Минимум роутов при одном фронтенд-разработчике. |

## 3. Группы пользователей

### Акторы системы

| Актор | Описание |
|---|---|
| **Гость** | Неавторизованный посетитель. Может посмотреть витрину сценариев и справочник, но не может сохранять прогресс. |
| **Обучающийся** | Авторизованный пользователь, проходящий тренировки. Основной актор. |
| **Контент-редактор** | Член команды, добавляющий и правящий сценарии в виде файлов. Работает вне UI. |
| **Система** | Движок прохождения, модуль оценки, модуль формирования разбора. |

### Целевые сегменты обучающихся

Сегменты не являются акторами системы и не задаются в интерфейсе: они нужны для
планирования контента. Кейс требует учить **разные группы пользователей**, а
значит набор сценариев должен покрывать разный опыт и разные схемы обмана.
Сегмент выводится из выбранной роли и уровня сложности сценария.

**1. Покупатель-новичок.**
Мало сделок, не знает механик безопасной сделки платформы. Уязвим к переводу
общения в сторонний мессенджер, к фишинговым ссылкам «оплата и доставка», к
давлению срочностью и заниженной цене. Задача обучения: сформировать рефлекс
«оплата и переписка — только внутри платформы».

**2. Опытный покупатель.**
Знает базовые правила, но теряет бдительность в нетипичных ситуациях:
поддельная служба поддержки, подмена реквизитов в уже начатой сделке, «курьер»,
запрашивающий данные карты. Нужны сценарии повышенной сложности с неочевидными
признаками.

**3. Частный продавец.**
Продаёт редко, мотивирован быстро закрыть сделку. Уязвим к схемам, где
мошенник выступает покупателем: поддельный скриншот перевода, ссылка «для
получения денег» с запросом данных карты, просьба назвать код из SMS «для
подтверждения доставки», схема с переплатой и возвратом разницы.

**4. Профессиональный продавец.**
Большой поток обращений, обрабатывает диалоги быстро и шаблонно. Уязвим к
массовым атакам и к фейковым сообщениям «от платформы» о блокировке аккаунта.
Ценит скорость прохождения и итоговую сводку.

## 4. Каталог рисковых ситуаций

Доменный словарь, на который опираются сценарии. Каждый признак риска имеет
стабильный идентификатор и используется в трёх местах: в разметке шагов
сценария (FR16), в обратной связи и в справочнике (FR28).

### Признаки риска на стороне покупателя

| ID | Признак | Суть |
|---|---|---|
| `RISK_OFF_PLATFORM_CHAT` | Увод в сторонний мессенджер | Просьба продолжить общение вне платформы, где нет модерации и истории |
| `RISK_PREPAY_OUTSIDE` | Предоплата вне платформы | Перевод на карту «чтобы забронировать товар» |
| `RISK_PHISHING_LINK` | Фишинговая ссылка | Ссылка на поддельную страницу «безопасной оплаты» или «доставки» |
| `RISK_URGENCY_PRESSURE` | Искусственная срочность | «Есть другой покупатель», «предложение сгорит через час» |
| `RISK_TOO_GOOD_PRICE` | Аномально низкая цена | Цена существенно ниже рынка как приманка |
| `RISK_CARD_DATA_REQUEST` | Запрос данных карты | «Курьер» или «оператор» просит номер карты и код с оборота |
| `RISK_FAKE_SUPPORT` | Поддельная поддержка | Сообщение якобы от платформы о блокировке или возврате |

### Признаки риска на стороне продавца

| ID | Признак | Суть |
|---|---|---|
| `RISK_SMS_CODE_REQUEST` | Запрос кода из SMS | Код «для подтверждения доставки» — на деле вход в аккаунт или перевод |
| `RISK_FAKE_PAYMENT_PROOF` | Поддельный скриншот оплаты | Требование отдать товар до фактического зачисления денег |
| `RISK_PAYOUT_LINK` | Ссылка «для получения денег» | Для «получения» перевода просят ввести реквизиты карты |
| `RISK_OVERPAYMENT` | Переплата и возврат разницы | Мошенник «ошибочно» переводит больше и просит вернуть разницу |
| `RISK_SHIP_BEFORE_PAYMENT` | Отправка до оплаты | Давление отправить товар без подтверждённой оплаты |
| `RISK_DOC_REQUEST` | Запрос персональных документов | Просьба прислать фото паспорта «для оформления доставки» |

### Безопасные паттерны поведения

Используются как «правильные» ветки и как содержание итоговых рекомендаций
(FR19): оставаться в чате платформы, использовать безопасную сделку, проверять
зачисление денег в приложении банка, никому не сообщать коды из SMS, не
переходить по ссылкам из переписки, обращаться в поддержку через официальный
раздел.

> Ссылки в сценариях (`avito-dostavka-pay.ru` и подобные) — имитация. Согласно
> SEC8 они не должны быть кликабельными и не должны вести на реальные ресурсы.

### План сценариев

Набор к защите зафиксирован. Каждый сценарий отрабатывает свою группу признаков,
пересечения минимальны — это позволяет статистике из FR26 показывать осмысленную
картину пробелов.

| # | Роль | Название | Сложность | Шагов | Признаки риска |
|---|---|---|---|---|---|
| 1 | Покупатель | Бронь по ссылке | Базовая | 6 | `RISK_PHISHING_LINK`, `RISK_PREPAY_OUTSIDE`, `RISK_URGENCY_PRESSURE` |
| 2 | Покупатель | Курьер и данные карты | Продвинутая | 8 | `RISK_CARD_DATA_REQUEST`, `RISK_FAKE_SUPPORT`, `RISK_OFF_PLATFORM_CHAT` |
| 3 | Продавец | Скриншот перевода | Базовая | 6 | `RISK_FAKE_PAYMENT_PROOF`, `RISK_SHIP_BEFORE_PAYMENT` |
| 4 | Продавец | Ссылка для получения денег | Продвинутая | 8 | `RISK_PAYOUT_LINK`, `RISK_SMS_CODE_REQUEST`, `RISK_DOC_REQUEST` |
| 5 | Покупатель | Слишком выгодная цена | Демонстрационная | 3 | `RISK_TOO_GOOD_PRICE`, `RISK_URGENCY_PRESSURE` |

Пятый сценарий короткий и предназначен для защиты: жюри проходит его за минуту и
видит полный цикл от выбора роли до разбора.

Признак `RISK_OVERPAYMENT` в наборе к защите не задействован и остаётся в
каталоге как резерв для расширения после MVP.

### Правила написания сценариев

Правила обязательны к соблюдению: часть из них проверяется валидатором при
загрузке (FR31), остальные проверяются на ревью контента.

**Структура (проверяется автоматически).**

- От 3 до 8 шагов на сценарий.
- Ровно три варианта на каждом шаге: один `safe`, один `risky`, один `critical`.
- Веса только из набора `+10` / `0` / `−10`, соответствующие `outcome`.
- Каждый вариант ведёт на существующий шаг либо в терминальный.
- Все шаги достижимы от стартового; из каждого шага достижим терминальный.
- Каждый шаг размечен хотя бы одним признаком риска из каталога выше.
- Каждый вариант содержит непустой `feedback`.

**Содержание (проверяется на ревью).**

1. **Опасный вариант должен быть правдоподобным.** Кейс прямо предупреждает: это
   не набор очевидных вопросов. Если `critical` выглядит явной глупостью, шаг
   ничему не учит. Ориентир: опасный вариант — это то, что сделал бы спешащий
   человек, а не невнимательный.
2. **Спорный вариант — это отсрочка, а не ошибка.** `risky` описывает продолжение
   диалога без защиты: уточнить, попросить подождать, согласиться обсудить.
   Пользователь не потерял деньги, но и не вышел из ситуации.
3. **Безопасный вариант ведёт к безопасному паттерну** из перечня выше, а не
   просто «отказаться и уйти».
4. **Обратная связь построена по схеме: признак → причина → альтернатива.**
   Формулировки «правильно» и «неправильно» не допускаются (USR4, требование
   кейса об обучающем объяснении).
5. **Ветвление сходится обратно в основную линию.** Отдельные концовки допустимы
   только на терминальных шагах. Иначе объём контента растёт экспоненциально, а
   поддерживать граф становится невозможно.
6. **Опасный выбор не обрывает сценарий досрочно**, кроме финального шага.
   Пользователь должен дойти до разбора, а не быть наказанным выходом из
   тренировки.
7. **Ссылки и реквизиты — имитация** (SEC8): домены не существуют, номера карт и
   телефонов не принадлежат реальным людям.
8. **Одна схема мошенничества на сценарий.** Смешение нескольких схем в одном
   диалоге размывает обучающий эффект и портит статистику по признакам (FR26).

**Пример шага.**

```json
{
  "code": "s3",
  "type": "dialog",
  "content": {
    "message": "Чтобы я снял объявление, внесите предоплату 2000 ₽ вот здесь: avito-dostavka-pay.ru"
  },
  "risk_signals": ["RISK_PHISHING_LINK", "RISK_PREPAY_OUTSIDE"],
  "options": [
    {
      "code": "a", "outcome": "critical", "score": -10, "next_step": "s4",
      "text": "Перейти по ссылке и оплатить",
      "feedback": "Домен только похож на официальный: настоящие страницы оплаты живут на avito.ru. Оплата по ссылке из переписки не защищена — деньги уходят напрямую мошеннику. Безопасный путь — кнопка оплаты внутри объявления."
    },
    {
      "code": "b", "outcome": "risky", "score": 0, "next_step": "s4",
      "text": "Спросить, почему нельзя через платформу",
      "feedback": "Вы не потеряли деньги, но остались в диалоге. Мошенник получит ещё одну попытку убедить вас — сейчас он сошлётся на «сбой в приложении». Причина отказа от платформы не имеет значения: сам отказ уже является признаком."
    },
    {
      "code": "c", "outcome": "safe", "score": 10, "next_step": "s5",
      "text": "Предложить оформить через безопасную сделку",
      "feedback": "Верно. Оплата остаётся внутри платформы, деньги переводятся продавцу только после получения товара. Добросовестный продавец на это согласится."
    }
  ]
}
```

## 5. Функциональные требования

Требования, помеченные **Доп.**, относятся к дополнительному функционалу и
реализуются после того, как основной путь работает полностью.

### Доступ и профиль

**FR1.** Система должна позволять пользователю зарегистрироваться, указав
уникальный ник и пароль.

**FR2.** Система должна позволять зарегистрированному пользователю
авторизоваться и завершать сессию.

**FR3.** Система должна связывать все попытки прохождения и агрегированный
прогресс с конкретной учётной записью.

**FR4.** Система должна позволять неавторизованному пользователю просматривать
витрину сценариев и справочник признаков риска, но не начинать тренировку.

### Витрина и выбор тренировки

**FR5.** Система должна позволять пользователю выбрать роль: покупатель или
продавец.

**FR6.** Система должна отображать список доступных для выбранной роли
сценариев с названием, кратким описанием, уровнем сложности и признаком того,
проходился ли сценарий ранее. При объёме набора в пять сценариев список выводится
целиком, без фильтрации, поиска и пагинации.

**FR7. Доп.** Система должна отображать по каждому сценарию лучший результат
пользователя, если попытки уже были.

### Прохождение сценария

**FR8.** Система должна создавать новую сессию прохождения при старте сценария
и фиксировать её начало.

**FR9.** Система должна последовательно выдавать пользователю шаги сценария в
виде реплик контрагента и вариантов ответа или действия.

**FR10.** Система должна принимать выбор пользователя на каждом шаге и
определять следующий шаг в зависимости от сделанного выбора (ветвление).

**FR11.** Система должна сохранять каждый выбор пользователя с привязкой к шагу
и времени.

**FR12. Доп.** Система должна позволять пользователю прервать прохождение и
позднее продолжить незавершённую сессию с того же шага.

**FR13.** Система должна запрещать изменение уже сделанного выбора в рамках
текущей сессии.

**FR14.** Система должна завершать сессию по достижении терминального шага
сценария.

### Обратная связь и обучение

**FR15.** Система должна после каждого выбора показывать обучающее объяснение:
к чему приводит выбранное действие и почему.

**FR16.** Система должна указывать в объяснении конкретные признаки риска,
присутствовавшие в этом шаге, со ссылкой на справочник.

**FR17.** Система должна визуально различать последствия выбора: безопасное
действие, спорное действие, опасное действие.

**FR18.** Система должна показывать по завершении сценария полный разбор:
перечень шагов, сделанные выборы, пропущенные признаки риска и рекомендуемое
поведение.

**FR19.** Система должна формировать по итогам прохождения список из нескольких
практических рекомендаций, применимых к реальной сделке.

### Оценка

**FR20.** Система должна начислять баллы за каждый выбор согласно весам,
заданным в сценарии, и вычислять итоговый балл сессии. Допустимые веса: `+10`
для безопасного действия, `0` для спорного, `−10` для опасного.

**FR21.** Система должна переводить итоговый балл в уровень безопасности:
80–100% — «устойчив», 60–79% — «внимателен», 0–59% — «уязвим». Пороги задаются
конфигурацией, а не константами в коде.

**FR22.** Система должна обеспечивать воспроизводимость оценки: одинаковая
последовательность выборов в одной версии сценария всегда даёт одинаковый
результат.

**FR23.** Система должна показывать пользователю сравнение с его предыдущей
попыткой по этому же сценарию.

### Прогресс

**FR24.** Система должна отображать историю всех попыток пользователя по
сценарию с датой и результатом. История выводится на экране результата.

**FR25.** Система должна отображать агрегированный прогресс: количество
пройденных сценариев из общего числа и лучший результат. Динамика показывается
как сравнение текущего результата с предыдущей попыткой по тому же сценарию, а не
как временной ряд.

**FR26. Доп.** Система должна отображать, какие признаки риска пользователь уже
научился распознавать, а какие продолжает пропускать.

**FR27.** Система должна предлагать пользователю следующий шаг: непройденный
сценарий или повторное прохождение сценария со слабым результатом.

### Справочник

**FR28. Доп.** Система должна предоставлять справочник признаков мошенничества
с описанием, стороной сделки и рекомендацией по безопасному поведению.

**FR29. Доп.** Система должна открывать карточку справочника по ссылке из
разбора прохождения.

### Контент

**FR30.** Система должна загружать сценарии из файлов в формате JSON при
инициализации базы данных.

**FR31.** Система должна валидировать структуру сценария при загрузке:
достижимость всех шагов, наличие терминальных шагов, корректность ссылок на
признаки риска.

**FR32.** Система должна хранить версию сценария и связывать сессию с той
версией, на которой она проходилась.

## 6. Нефункциональные требования

### Security

**SEC1.** Пароли пользователей должны храниться исключительно в виде хеша с
солью (bcrypt), в открытом виде не храниться и не логироваться.

**SEC2.** Доступ к сессиям прохождения и прогрессу должен быть возможен только
для их владельца; попытка обратиться к чужому ресурсу возвращает ошибку доступа
без раскрытия факта существования ресурса.

**SEC3.** Все входные данные должны валидироваться на стороне сервера;
клиентская валидация не считается достаточной.

**SEC4.** Обращения к базе данных должны выполняться только через
параметризованные запросы.

**SEC5.** Секреты (пароль и данные подключения к БД, ключ подписи токенов)
должны задаваться через переменные окружения и не попадать в репозиторий.

**SEC6.** Сообщения об ошибках, отдаваемые клиенту, не должны раскрывать
внутреннее устройство системы: стек вызовов, SQL-запросы, версии компонентов.

**SEC7.** Логи не должны содержать паролей, токенов и тел запросов
аутентификации.

**SEC8.** Обучающие материалы не должны содержать работоспособных ссылок на
внешние ресурсы — фишинговые ссылки в сценариях должны быть имитацией и не
вести никуда.

### Usability

**USR1.** Путь от открытия главной страницы до первого шага тренировки должен
занимать не более трёх действий пользователя.

**USR2.** На каждом шаге прохождения пользователю должно быть очевидно, в какой
он роли, на каком шаге из скольких находится и какое действие от него ожидается.

**USR3.** Обратная связь после выбора должна появляться немедленно, без
перезагрузки страницы и без потери контекста диалога.

**USR4.** Объяснение должно быть сформулировано обучающим языком: указывать
признак, причину и безопасную альтернативу, а не только вердикт.

**USR5.** Интерфейс должен корректно отображаться на экранах шириной от 360 px.

**USR6.** Все состояния экрана — загрузка, пустой список, ошибка запроса — должны
иметь явное визуальное представление.

**USR7.** Прерванную тренировку должно быть возможно продолжить с главной
страницы без поиска по разделам.

**USR8.** Тексты интерфейса и контента — на русском языке.

### Reliability

**REL1.** Приложение должно полностью разворачиваться командой
`docker compose up` на чистой машине без ручных дополнительных шагов.

**REL2.** Незавершённая сессия прохождения должна сохраняться и оставаться
доступной после перезапуска сервиса.

**REL3.** Все ошибки должны обрабатываться явно; паника в обработчике не должна
приводить к остановке сервиса.

**REL4.** Приложение должно завершаться корректно по сигналу остановки,
дожидаясь завершения текущих запросов.

### Maintainability

**MNT1.** Код должен проходить проверку `golangci-lint` с конфигурацией из
`.golangci.yaml` в корне проекта.

**MNT2.** Код фронтенда должен проходить проверку ESLint и форматирование
Prettier.

**MNT3.** Все проверки (линтер, форматирование, тесты) должны автоматически
выполняться в CI при создании pull request или перед слиянием в основную ветку.

**MNT4.** Контракт API должен быть зафиксирован в OpenAPI-спецификации,
являющейся единственным источником истины для фронтенда и бэкенда.

**MNT5.** Покрытие кода тестами должно достигать 60%.

**MNT6.** Логирование должно быть структурированным, с уровнями и с
идентификатором запроса.

### Соглашения разработки

Следующие правила не являются формальными требованиями, но обязательны к
соблюдению и фиксируются в `AGENTS.md`. Они выведены из принципов, принятых
командой, и напрямую влияют на достижимость MNT5.

- Слои приложения разделены по зонам ответственности: транспорт, бизнес-логика,
  доступ к данным. Обратные зависимости запрещены.
- Обмен данными между слоями и с клиентом производится через DTO; доменные
  структуры не сериализуются в HTTP-ответ напрямую.
- Движок ветвления, расчёт оценки и валидатор сценариев реализуются как функции
  без внешних зависимостей — иначе 60% покрытия недостижимы без тяжёлых
  интеграционных тестов.
- Добавление нового сценария не требует изменения кода.
- Приложение не принимает трафик до успешного применения миграций и установления
  соединения с БД; это техническое условие выполнения REL1.

## 8. Прецеденты использования

### Прецедент: Регистрация пользователя

**ID:** 1
**Требования:** FR1, FR3, SEC1
**Краткое описание:** Гость создаёт учётную запись, чтобы его прогресс
сохранялся между посещениями.
**Главные актёры:** Гость, Система.
**Предусловия:** Пользователь не авторизован.

**Основной поток:**
1. Гость открывает форму регистрации.
2. Гость вводит ник и пароль.
3. Система валидирует данные на сервере: ник свободен, пароль удовлетворяет
   требованиям.
4. Система создаёт учётную запись, сохраняя хеш пароля.
5. Система создаёт сессию и возвращает токен доступа.
6. Система перенаправляет пользователя на витрину сценариев.

**Альтернативные потоки:**
- 3а. Ник занят → система сообщает об этом, поток возвращается на шаг 2.
- 3б. Пароль не удовлетворяет требованиям → система показывает требования,
  поток возвращается на шаг 2.

**Постусловия:** Пользователь авторизован, учётная запись создана.

---

### Прецедент: Выбор роли и сценария

**ID:** 2
**Требования:** FR4, FR5, FR6, FR7
**Краткое описание:** Пользователь выбирает, за кого он будет проходить
тренировку, и подбирает сценарий.
**Главные актёры:** Гость, Обучающийся, Система.
**Предусловия:** Отсутствуют.

**Основной поток:**
1. Пользователь открывает витрину.
2. Система отображает переключатель ролей «Покупатель / Продавец».
3. Пользователь выбирает роль.
4. Система запрашивает список сценариев для выбранной роли, а для авторизованного
   пользователя — также результаты его предыдущих попыток.
5. Система отображает карточки сценариев: название, описание, сложность,
   статус прохождения и лучший результат.
6. Обучающийся выбирает сценарий и подтверждает старт.

**Альтернативные потоки:**
- 5а. По выбранной роли нет сценариев → система показывает пустое состояние с
  предложением сменить роль.
- 6а. Пользователь не авторизован → система предлагает войти или
  зарегистрироваться, сохранив выбранный сценарий.
- 6б. По выбранному сценарию есть незавершённая сессия → система предлагает
  продолжить её или начать заново (см. прецедент 8).

**Постусловия:** Выбран сценарий для прохождения.

---

### Прецедент: Прохождение шага сценария

**ID:** 3
**Требования:** FR8–FR11, FR13, FR15–FR17
**Краткое описание:** Обучающийся принимает решение в спорном моменте сделки и
получает обучающую обратную связь.
**Главные актёры:** Обучающийся, Система.
**Предусловия:** Сессия прохождения создана и не завершена.

**Основной поток:**
1. Система отображает текущий шаг: реплики контрагента и контекст ситуации.
2. Система отображает доступные варианты действия, роль пользователя и позицию
   в сценарии.
3. Обучающийся выбирает вариант.
4. Система проверяет, что шаг ещё не отвечен, и фиксирует выбор в сессии.
5. Система начисляет баллы согласно весу выбранного варианта.
6. Система отображает последствие выбора и обучающее объяснение с указанием
   признаков риска, присутствовавших в шаге, визуально различая безопасное,
   спорное и опасное действие.
7. Система определяет следующий шаг по ветвлению, заданному выбранным вариантом.
8. Обучающийся подтверждает переход далее.
9. Система отображает следующий шаг; поток повторяется с пункта 1.

**Альтернативные потоки:**
- 4а. Шаг уже отвечен → система возвращает ранее зафиксированный результат, не
  изменяя состояние сессии и не начисляя баллы повторно (FR13).
- 4б. Переданного варианта не существует в этом шаге → система возвращает ошибку
  валидации, состояние не меняется (SEC3).
- 7а. Следующий шаг является терминальным → выполняется прецедент 4.

**Постусловия:** Выбор зафиксирован, сессия переведена на следующий шаг.

---

### Прецедент: Завершение тренировки и получение оценки

**ID:** 4
**Требования:** FR14, FR18–FR23, FR27
**Краткое описание:** Обучающийся доходит до конца сценария и получает
мотивирующую оценку своих решений.
**Главные актёры:** Обучающийся, Система.
**Предусловия:** Достигнут терминальный шаг сценария.

**Основной поток:**
1. Система помечает сессию завершённой и фиксирует время окончания.
2. Система вычисляет итоговый балл как сумму баллов за все выборы.
3. Система определяет уровень безопасности по итоговому баллу.
4. Система формирует перечень признаков риска, которые были в сценарии, с
   отметкой, распознал их пользователь или пропустил.
5. Система формирует список практических рекомендаций.
6. Система сравнивает результат с предыдущей попыткой пользователя по этому
   сценарию, если такая была.
7. Система отображает экран результата: балл, уровень, динамика, разбор,
   рекомендации.
8. Система предлагает следующий шаг: пройти новый сценарий или повторить
   текущий.

**Альтернативные потоки:**
- 6а. Предыдущих попыток не было → блок сравнения не отображается.

**Постусловия:** Сессия завершена, результат сохранён и включён в прогресс.

---

### Прецедент: Просмотр детального разбора решений

**ID:** 5
**Требования:** FR18, FR29
**Краткое описание:** Обучающийся разбирает свои решения по шагам, чтобы понять,
что именно было упущено.
**Главные актёры:** Обучающийся, Система.
**Предусловия:** Сессия завершена.

**Основной поток:**
1. Обучающийся открывает разбор с экрана результата.
2. Система отображает список шагов в порядке прохождения.
3. По каждому шагу система показывает: ситуацию, выбранный вариант, его
   последствие, безопасную альтернативу и присутствовавшие признаки риска.
4. Обучающийся открывает карточку признака риска из справочника.
5. Система отображает описание признака и рекомендацию по поведению.

**Альтернативные потоки:**
- 4а. Справочник не реализован → признаки риска отображаются как текст без
  перехода.

**Постусловия:** Пользователь ознакомлен с разбором.

---

### Прецедент: Повторное прохождение сценария

**ID:** 6
**Требования:** FR22, FR23, FR25
**Краткое описание:** Обучающийся проходит сценарий заново, чтобы улучшить
результат и убедиться, что стал распознавать риски лучше.
**Главные актёры:** Обучающийся, Система.
**Предусловия:** По сценарию есть хотя бы одна завершённая сессия.

**Основной поток:**
1. Обучающийся выбирает повторное прохождение.
2. Система создаёт новую сессию, не изменяя предыдущие.
3. Обучающийся проходит сценарий (прецедент 3).
4. По завершении система отображает результат вместе с дельтой относительно
   лучшей предыдущей попытки.
5. Система обновляет агрегированный прогресс пользователя.

**Постусловия:** Создана новая завершённая сессия, история попыток пополнена.

---

### Прецедент: Просмотр прогресса

**ID:** 7
**Требования:** FR24–FR27, SEC2
**Краткое описание:** Обучающийся оценивает, как менялись его результаты и что
осталось изучить.
**Главные актёры:** Обучающийся, Система.
**Предусловия:** Пользователь авторизован.

**Основной поток:**
1. Обучающийся открывает раздел прогресса.
2. Система вычисляет агрегаты: число пройденных сценариев, средний балл, лучший
   балл, динамику по датам.
3. Система вычисляет статистику по признакам риска: распознанные и регулярно
   пропускаемые.
4. Система отображает историю попыток с возможностью перейти к разбору любой.
5. Система предлагает следующий шаг обучения.

**Альтернативные потоки:**
- 2а. Завершённых сессий нет → система отображает пустое состояние с призывом
  начать первую тренировку.

**Постусловия:** Пользователь ознакомлен со своим прогрессом.

### Прецедент: Продолжение прерванной тренировки (Доп.)

**ID:** 8
**Требования:** FR12, USR7, REL2
**Краткое описание:** Обучающийся возвращается к сценарию, который не успел

**Главные актёры:** Обучающийся, Система.

**Основной поток:**

2. Обучающийся выбирает продолжение.
3. Система восстанавливает сессию, включая накопленный балл и историю выборов.
4. Система отображает шаг, на котором прохождение было прервано.
5. Обучающийся продолжает прохождение (прецедент 3).

**Альтернативные потоки:**
- 2а. Обучающийся выбирает «начать заново» → система помечает старую сессию
  прерванной и создаёт новую.

**Постусловия:** Прохождение продолжено или начато заново.

### Прецедент: Загрузка и валидация сценария

**ID:** 10
**Требования:** FR30–FR32
**Краткое описание:** Контент-редактор добавляет новый сценарий в систему.
**Главные актёры:** Контент-редактор, Система.
**Предусловия:** Сценарий описан в JSON согласно схеме.

**Основной поток:**
1. Контент-редактор помещает файл сценария в каталог сидов.
2. Контент-редактор запускает команду загрузки контента.

## 9. Доменная модель

### Ключевые сущности

| Сущность | Назначение | Основные атрибуты |
|---|---|---|
| `User` | Учётная запись обучающегося | id, nickname, password_hash, created_at |
| `Scenario` | Сценарий тренировки | id, code, version, role, title, description, difficulty, is_active |
| `Step` | Шаг сценария (реплика и ситуация) | id, scenario_id, code, type (dialog / terminal), content, risk_signal_codes |
| `Option` | Вариант действия на шаге | id, step_id, code, text, outcome (safe / risky / critical), score, feedback, next_step_code |
| `RiskSignal` | Признак риска из справочника | code, side (buyer / seller), title, description, how_to_act |
| `Session` | Попытка прохождения | id, user_id, scenario_id, scenario_version, status, current_step_code, score, started_at, finished_at |
| `Answer` | Зафиксированный выбор | id, session_id, step_code, option_code, score_delta, answered_at |

### Ключевые инварианты

- В рамках одной сессии на один шаг может существовать не более одного `Answer`
  (FR13). Обеспечивается уникальным индексом на паре (session_id, step_code).
- `Session.score` равен сумме `Answer.score_delta` по сессии. Фиксация ответа и
  обновление балла выполняются в одной транзакции.
- `Session` ссылается на конкретную версию сценария; изменение контента не меняет
  результатов уже завершённых сессий (FR32).
- Каждый `Step` типа `dialog` имеет ровно три `Option` с различными `outcome`
  (`safe`, `risky`, `critical`); каждый `Option` указывает на существующий шаг
  либо ведёт в терминальный (FR31).
- Граф шагов не содержит недостижимых вершин и всегда завершается.

### Правило оценки

#### Шкала весов

Вес варианта определяется его `outcome` и не может принимать других значений.

| `outcome` | Вес | Смысл |
|---|---|---|
| `safe` | **+10** | Пользователь распознал риск и поступил правильно |
| `risky` | **0** | Не совершил ошибки, но и не защитился: продолжил диалог, отложил решение |
| `critical` | **−10** | Совершил действие, которое в реальности стоило бы денег или аккаунта |

Ограничение тремя значениями обеспечивает сопоставимость оценок между
сценариями. При свободных весах максимум в одном сценарии составил бы 40, а в
другом 120, и одинаковый процент означал бы разное качество решений.

#### Формула

```
n       = количество сделанных выборов
score   = Σ весов выбранных вариантов
max     =  10 × n     (все выборы безопасны)
min     = −10 × n     (все выборы опасны)
percent = (score − min) × 100 / (max − min)
level   = порог, в который попадает percent
```

Нормализация ведётся от числа фактически сделанных выборов, а не от «лучшего
пути» по графу. При ветвлении ветки имеют разную длину, и «лучший путь» был бы
неоднозначен; выбранный подход не зависит от структуры графа вообще. Побочный
эффект: `percent` не может выйти за пределы 0–100 математически, отдельная
проверка границ не нужна.

#### Пример расчёта

Сценарий «Бронь по ссылке», 6 шагов. Первая попытка:

| Шаг | Выбор пользователя | `outcome` | Вес | Накоплено |
|---|---|---|---|---|
| s1 | Спросил, почему не через платформу | `risky` | 0 | 0 |
| s2 | Отказался переходить в мессенджер | `safe` | +10 | 10 |
| s3 | Открыл ссылку «оплата брони» | `critical` | −10 | 0 |
| s4 | Заметил подмену домена | `safe` | +10 | 10 |
| s5 | Согласился внести предоплату | `critical` | −10 | 0 |
| s6 | Обратился в поддержку | `safe` | +10 | **10** |

```
n = 6, score = 10, max = 60, min = −60
percent = (10 + 60) × 100 / 120 = 58%  →  «уязвим»
```

Вторая попытка того же пользователя (пять `safe`, один `risky`):

```
score = 50  →  percent = (50 + 60) × 100 / 120 = 92%  →  «устойчив»
delta = +34 процентных пункта
```

Именно эта пара значений отображается на экране результата (FR23, FR25).

#### Краевые случаи

| Поведение | score | percent | Уровень |
|---|---|---|---|
| Все выборы безопасны | +60 | 100% | Устойчив |
| Все выборы спорные | 0 | 50% | Уязвим |
| Все выборы опасны | −60 | 0% | Уязвим |

Нижний порог установлен на 60%, а не на 50%, намеренно. При пороге 50%
пользователь, не принявший ни одного верного решения и только затягивавший
диалог, получал бы ровно 50% и попадал в «внимателен». Это неверное сообщение:
уклонение от решения не является безопасным поведением. При пороге 60% для
выхода из «уязвим» требуется хотя бы несколько верных решений.

В коротком демонстрационном сценарии (`n = 3`) шаг шкалы составляет
`100 / (2 × 3) ≈ 17%`, возможные значения: 100, 83, 67, 50, 33, 17, 0. Пороги
80 и 60 попадают между значениями удачно: одна спорная реплика даёт 83%
(«устойчив»), одна опасная — 67% («внимателен»).

#### Реализация

```go
type Outcome string

const (
    OutcomeSafe     Outcome = "safe"
    OutcomeRisky    Outcome = "risky"
    OutcomeCritical Outcome = "critical"
)

var weights = map[Outcome]int{
    OutcomeSafe: 10, OutcomeRisky: 0, OutcomeCritical: -10,
}

type Thresholds struct {
    Resilient int `yaml:"resilient"` // 80
    Attentive int `yaml:"attentive"` // 60
}

func Evaluate(answers []Answer, t Thresholds) Result {
    n := len(answers)
    if n == 0 {
        return Result{}
    }

    score := 0
    for _, a := range answers {
        score += a.ScoreDelta
    }

    max, min := 10*n, -10*n
    percent := (score - min) * 100 / (max - min)

    return Result{Score: score, Percent: percent, Level: levelFor(percent, t)}
}
```

Функция не обращается ни к БД, ни к HTTP, ни к структуре сценария — только к
списку ответов. Пороги приходят из конфигурации, что обеспечивает FR22 и делает
функцию тестируемой без инфраструктуры (вклад в MNT5).

Обязательные тест-кейсы: все безопасные, все спорные, все опасные, обе границы
порогов, незавершённая сессия с двумя ответами, пустой список ответов
(защита от деления на ноль).

#### Оценка и статистика по признакам — независимые метрики

`percent` отвечает на вопрос «насколько безопасно вёл себя пользователь».
Статистика из FR26 отвечает на другой вопрос — «какие конкретно схемы он не
распознаёт». Признак считается пропущенным, если на шаге, размеченном этим
признаком, пользователь выбрал `risky` или `critical`.

Эти метрики не выводятся одна из другой: можно набрать 75% и при этом стабильно
проваливаться на `RISK_SMS_CODE_REQUEST` во всех попытках. Балл этого не
покажет, а статистика покажет — в этом её ценность для обучения.

### Принципы

**Монолит, а не микросервисы.** Объём домена не оправдывает сетевые границы, а
команда из четырёх человек за неделю потеряет на инфраструктуре больше, чем
приобретёт. Разделение обеспечивается модулями внутри одного бинарника.

**Три слоя, зависимости только вниз.** Транспорт знает о сервисах, сервисы — о
репозиториях, репозитории — о БД. Обратные зависимости запрещены и проверяются
на ревью.

**Ядро домена без внешних зависимостей.** Движок ветвления, расчёт оценки и
валидатор сценариев не обращаются к БД и не знают о HTTP. Это прямое следствие
MNT5: 60% покрытия достигаются юнит-тестами чистых функций, а не поднятием
контейнеров в тестах.

**DTO на границах.** Доменные структуры не сериализуются в HTTP напрямую; для
каждого эндпоинта существуют явные request/response DTO. Это защищает от
случайной утечки полей и позволяет менять домен, не ломая контракт.

**Только синхронные операции.** Все обработчики завершают работу в рамках
запроса. Внешних интеграций у сервиса нет.

**Контракт первичен.** OpenAPI-спецификация фиксируется в первый день (MNT4).
Фронтенд генерирует по ней типы и работает по моку, не дожидаясь готовности
бэкенда.

**Контент отделён от кода.** Сценарии — версионируемые данные. Это позволяет
писать контент параллельно с движком и масштабировать решение без релиза.

## 11. Обоснование выбора БД

**Выбор: PostgreSQL 16.**

**Почему реляционная СУБД.** Основные данные приложения — связанные сущности с
устойчивой схемой: пользователи, сессии, ответы, сценарии. Ключевые запросы —
агрегации по истории попыток (FR25, FR26): средний балл, динамика, статистика по
признакам риска. Это ровно тот класс задач, где SQL с группировками и оконными
функциями даёт готовое решение, а документная модель потребовала бы считать
агрегаты в коде приложения.

**Почему именно PostgreSQL.**

1. **Транзакционность.** Фиксация ответа, начисление баллов и перевод сессии на
   следующий шаг должны быть атомарны, иначе нарушается инвариант
   `score = Σ score_delta`. ACID-гарантии решают это без ручных компенсаций.
2. **JSONB для контента.** Тело шага сценария удобно хранить как JSONB: структура
   контента может эволюционировать, при этом реляционные связи и индексы
   сохраняются. Гибридный подход — жёсткая схема там, где нужна целостность, и
   гибкая там, где нужен контент.
3. **Ограничения целостности на уровне БД.** Уникальный индекс на паре
   (session_id, step_code) делает FR13 гарантией схемы, а не соглашением в коде.
4. **Простота развёртывания.** Официальный образ поднимается в Docker Compose
   одной секцией с health-check, что напрямую поддерживает REL1, а сохранение
   данных в томе — REL2.

**Рассмотренные альтернативы.**

| Вариант | Почему отклонён |
|---|---|
| MongoDB | Сценарий хорошо ложится на документы, но история попыток и прогресс требуют агрегаций по связанным коллекциям. Отсутствие внешних ключей переносит контроль целостности в код приложения — риск для команды, работающей параллельно. |
| SQLite | Достаточна по объёму данных, но плохо переносит конкурентную запись и хранение в томе контейнера, а также усложняет проверку жюри при одновременном доступе. |
| MySQL | Функционально подходит, но уступает по работе с JSON и по выразительности оконных функций, нужных для расчёта динамики результатов. |
| Redis как основное хранилище | Не подходит: данные должны переживать перезапуск (REL2) и допускать произвольные аналитические запросы. Может быть добавлен позже как кеш, в MVP не нужен. |

## 12. Технологии

### Frontend

- **React 18+**, **TypeScript** — обязательное требование кейса.
- **Vite** — быстрая сборка и dev-server, минимум конфигурации.
- **Ant Design** — большой набор готовых компонентов (карточки, шаги, статистика,
  прогресс), что критично при одном фронтенд-разработчике и сроке в неделю.
- **React Query** — работа с серверным состоянием, кеширование, состояния
  загрузки и ошибок из коробки (поддерживает USR6).
- **Zustand или React Context** — локальное клиентское состояние. Redux избыточен:
  почти всё состояние приложения является серверным.
- **Axios** — HTTP-клиент с перехватчиками для авторизации и обработки ошибок.
- **ESLint + Prettier** — MNT2, с обоснованием набора правил в README.
- **openapi-typescript** — генерация типов из `api/openapi.yaml`, единый контракт
  без ручной синхронизации (MNT4).

### Backend

- **Go 1.22+** — обязательное требование кейса.
- **chi** — минималистичный HTTP-роутер поверх стандартной библиотеки; middleware
  для request id, логирования, recover (REL3) и CORS.
- **pgx** — драйвер PostgreSQL, работа без ORM: явные параметризованные запросы
  (SEC4), предсказуемое поведение, соответствие принципу KISS.
- **goose** — миграции схемы, применяются до старта приложения.
- **log/slog** — структурированное логирование из стандартной библиотеки (MNT6).
- **golang-jwt** — токены доступа.
- **bcrypt** — хеширование паролей (SEC1).
- **testify** — утверждения в юнит-тестах (MNT5).
- **golangci-lint** — конфигурация `.golangci.yaml` в корне проекта (MNT1).

### Инфраструктура

- **Docker + Docker Compose** — обязательное требование кейса. Сервисы:
  `postgres`, `backend`, `frontend`. Health-check у БД, зависимость запуска
  бэкенда от её готовности, том для сохранения данных.
- **Makefile** — единые команды для всей команды: `up`, `down`, `lint`, `test`,
  `cover`, `migrate`, `seed`, `generate`.
- **GitHub Actions** — MNT3: линтеры, форматирование и тесты на каждом pull
  request, проверка порога покрытия из MNT5.

## 13. Разбиение на модули и распределение работ

Модули выбраны так, чтобы пересечение по файлам было минимальным.

| Модуль | Зона ответственности | Роль |
|---|---|---|
| **M1. Ядро и платформа** | Скелет проекта, config, logger, подключение к БД, миграции, middleware, graceful shutdown, docker-compose, Makefile, линтеры, CI | Backend 1 |
| **M2. Движок прохождения** | Сессии, ветвление, фиксация ответов, валидация сценариев, юнит-тесты движка | Backend 1 → далее Backend 2 |
| **M3. Оценка и прогресс** | Скоринг, уровни, агрегаты прогресса, сравнение попыток, статистика по признакам риска | Backend 2 |
| **M4. Аутентификация и профиль** | Регистрация, вход, токены, проверка владельца ресурса | Backend 3 |
| **M5. Контент** | Схема сценария, написание сценариев для обеих ролей, справочник признаков, сиды и валидатор | Backend 3 |
| **M6. Интерфейс** | Все экраны, компонент диалога, состояния, интеграция с API | Frontend |

**Точки стыковки:**
`api/openapi.yaml` — контракт между M6 и всем бэкендом, фиксируется в день 1.
Схема сценария (JSON Schema) — контракт между M5 и M2, фиксируется в день 1.
Каталог признаков риска из раздела 4 — общий словарь для M5, M3 и M6.

**Ответственность за покрытие (MNT5).** Порог 60% — общекомандный, но набирается
неравномерно: основной вклад дают M2 и M3, где логика тестируется без
инфраструктуры. Каждый разработчик пишет тесты к своему модулю в той же задаче,
а не отдельным этапом в конце — иначе к дню 7 порог не будет взят, и CI из MNT3
заблокирует слияние.
