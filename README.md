# Антискам тренажёр

Интерактивный тренажёр безопасных сделок для классифайда. Пользователь
выбирает роль покупателя или продавца, проходит симуляцию диалога с
контрагентом, принимает решения в спорных моментах, видит последствия выбора
и получает объяснение, какие признаки риска присутствовали в сценарии.

Цель продукта — перенос опыта тренировки в реальные сделки: научиться
распознавать тревожные признаки **до** совершения рискованного действия.

> Решение по [Кейсу 5](Кейс%205.pdf). Требования, прецеденты и обоснования
> решений — в [`Сase-analysis.md`](Сase-analysis.md).

## Быстрый старт

Нужен только Docker с плагином Compose.

```bash
docker compose up --build
```

Приложение поднимается целиком: PostgreSQL, миграции, загрузка контента,
API. Дополнительных шагов не требуется.

| Что | Адрес |
|---|---|
| Интерфейс | http://localhost:3000 |
| API | http://localhost:8080 |
| Проба готовности | http://localhost:8080/readyz |

Остановить с сохранением данных — `docker compose down`, вместе с данными —
`docker compose down -v`.

Значения по умолчанию рассчитаны на локальный запуск. Для деплоя скопируйте
`.env.example` в `.env` и задайте как минимум `JWT_SECRET` и

## Что умеет приложение

- Регистрация по нику и паролю; прогресс привязан к учётной записи.
- Гостевой просмотр витрины сценариев и справочника без регистрации.
- Выбор роли — покупатель или продавец — и сценария нужной сложности.
- Прохождение диалога с ветвлением: выбор меняет ход разговора, а не только
  счёт.
- Обучающее объяснение после каждого выбора с указанием признаков риска.
- Итоговый разбор: балл, уровень безопасности, пошаговый разбор решений,
  карта распознанных и пропущенных признаков, практические рекомендации.
- Сравнение с предыдущей попыткой и предложение следующего шага обучения.
- История попыток по каждому сценарию.

Дополнительный функционал: справочник признаков мошенничества, статистика по
признакам риска, продолжение прерванной тренировки, лучший результат на
витрине.

## Как устроено обучение

**Три варианта на каждом шаге.** Безопасный, спорный и опасный. Спорный — это
не «почти правильно», а отсрочка: диалог продолжается, но защиты не
появилось. Такая сетка одинакова во всех сценариях, поэтому оценки
сопоставимы между собой.

**Объяснение вместо вердикта.** Обратная связь строится по схеме
«признак → причина → альтернатива». Слов «правильно» и «неправильно» в
контенте нет: пользователь должен унести из тренировки признак, по которому
узнает схему в реальной переписке, а не оценку своего ответа.

**Оценка.** Каждый выбор весит `+10`, `0` или `−10`. Итог нормируется от числа
фактически сделанных выборов:

```
percent = (score − min) × 100 / (max − min),   где max = 10n, min = −10n
```

Уровень: 80–100% — «устойчив», 60–79% — «внимателен», 0–59% — «уязвим».
Нижний порог намеренно 60, а не 50: пользователь, который только затягивал
диалог, не должен получать «внимателен» — уклонение от решения не является
безопасным поведением.

**Прогресс.** Динамика показывается сравнением с предыдущей попыткой по тому
же сценарию, а не графиком: это прямо отвечает на вопрос «стал ли я лучше».
Отдельно считается статистика по признакам риска — она отвечает на другой
вопрос: «какие схемы я всё ещё не распознаю». Метрики независимы: можно
набрать 75% и стабильно проваливаться на запросе кода из SMS.

Каталог признаков риска и правила написания сценариев —
[`backend/seed/README.md`](backend/seed/README.md).

## API

Контракт зафиксирован в [`api/openapi.yaml`](api/openapi.yaml) и является
единственным источником истины для фронтенда и бэкенда.

```bash
make api-docs    # документация на http://localhost:8081
make api-lint    # проверка спецификации
make api-mock    # мок-сервер на :4010 — фронтенд без бэкенда
```

Базовый префикс — `/api/v1`. Авторизация — `Authorization: Bearer <token>`.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/register` | Регистрация |
| `POST` | `/auth/login` | Вход |
| `POST` | `/auth/logout` | Выход |
| `GET` | `/auth/me` | Текущий пользователь |
| `GET` | `/scenarios` | Витрина сценариев для роли |
| `GET` | `/scenarios/{code}` | Карточка сценария перед стартом |
| `GET` | `/scenarios/{code}/attempts` | История попыток по сценарию |
| `POST` | `/sessions` | Старт тренировки |
| `GET` | `/sessions/{id}` | Состояние сессии и текущий шаг |
| `POST` | `/sessions/{id}/answers` | Зафиксировать выбор и получить разбор шага |
| `GET` | `/sessions/{id}/result` | Итоговый разбор прохождения |
| `POST` | `/sessions/{id}/abandon` | Прервать тренировку |
| `GET` | `/progress` | Прогресс, продолжение тренировки, следующий шаг |
| `GET` | `/progress/signals` | Статистика по признакам риска |
| `GET` | `/risk-signals` | Справочник признаков риска |
| `GET` | `/risk-signals/{code}` | Карточка признака риска |

Пробы состояния вне префикса: `GET /healthz`, `GET /readyz`.

Ошибки приходят единым конвертом с машинным кодом — клиент принимает решения
по `error.code`, а не по тексту:

```json
{
  "error": {
    "code": "session_already_active",
    "message": "По этому сценарию есть незавершённая тренировка",
    "details": { "session_id": "3f1c9c1e-6f2a-4f7f-9a7b-6b5f2e2f1a11" }
  },
  "request_id": "01J8XQ2M7K3ZC0P4B6R9V2T5"
}
```

Две детали контракта, которые легко упустить:

- До ответа на шаг клиент **не получает** `outcome`, вес и `feedback`
  вариантов, а также признаки риска шага. Иначе безопасный вариант
  вычисляется из ответа API и тренажёр перестаёт учить.
- Повторная отправка ответа на уже отвеченный шаг возвращает сохранённый
  результат с `already_answered: true`, не меняя состояние и не начисляя
  баллы повторно.

## Архитектура

```
┌──────────────────────────────────────────────────────────┐
│                    Docker Compose                        │
│  ┌────────────────┐      ┌──────────────────────────┐    │
│  │   frontend     │      │        backend           │    │
│  │  React + TS    │─────▶│      Go, REST API        │    │
│  │  nginx         │ HTTP │  ┌────────────────────┐  │    │
│  └────────────────┘      │  │ transport (HTTP)   │  │    │
│                          │  ├────────────────────┤  │    │
│                          │  │ service            │  │    │
│                          │  ├────────────────────┤  │    │
│                          │  │ repository         │  │    │
│                          │  └────────────────────┘  │    │
│                          └────────────┬─────────────┘    │
│                          ┌────────────▼─────────────┐    │
│                          │       PostgreSQL         │    │
│                          └──────────────────────────┘    │
└──────────────────────────────────────────────────────────┘
```

Монолит с тремя слоями и зависимостями только вниз. Доменное ядро — движок
ветвления, расчёт оценки и валидатор сценариев — не знает ни о БД, ни о HTTP
и покрывается юнит-тестами без инфраструктуры.

```
.
├── api/openapi.yaml          контракт API
├── backend/
│   ├── cmd/api/              точка входа сервиса
│   ├── cmd/seed/             загрузчик контента
│   ├── internal/
│   │   ├── domain/           чистое ядро: оценка, ветвление, валидация
│   │   ├── service/          бизнес-логика
│   │   ├── repository/       доступ к данным
│   │   ├── transport/http/   маршруты, middleware, DTO
│   │   ├── config/           конфигурация из окружения
│   │   ├── logger/           структурированные логи
│   │   └── storage/postgres/ подключение и миграции
│   ├── migrations/           схема БД (goose)
│   └── seed/                 сценарии и справочник признаков риска
├── frontend/                 интерфейс (React + TypeScript)
├── docker-compose.yml
├── Makefile
├── AGENTS.md                 соглашения разработки
└── Сase-analysis.md          требования и обоснования решений
```

**Почему PostgreSQL.** Ключевые запросы приложения — агрегации по истории
попыток: средний и лучший результат, динамика, статистика по признакам риска.
Это ровно тот класс задач, где SQL с группировками и оконными функциями даёт
готовое решение. Транзакции обеспечивают инвариант «балл сессии равен сумме
баллов ответов», а уникальный индекс по паре `(session_id, step_code)`
превращает запрет менять сделанный выбор в гарантию схемы, а не в соглашение
в коде. Тело шага хранится в JSONB — контент может эволюционировать без
миграций. Развёрнутое сравнение с MongoDB, SQLite, MySQL и Redis — в разделе
11 анализа.

## Стек и зависимости

**Backend:** Go, chi (роутер), pgx (драйвер PostgreSQL без ORM), goose
(миграции), golang-jwt, bcrypt, log/slog, testify, golangci-lint.

**Frontend:** React 18, TypeScript, Vite, Ant Design, React Query, Axios,
ESLint, Prettier, openapi-typescript.

**Инфраструктура:** Docker Compose (postgres + backend + frontend),
GitHub Actions.

ORM не используется: запросы пишутся явно и параметризованно — это
предсказуемее и напрямую закрывает требование о защите от инъекций.

## Тесты и линтеры

```bash
make test        # go test ./... -race
make cover       # покрытие, цель MNT5 — 60%
make lint        # golangci-lint по .golangci.yaml
make api-lint    # проверка OpenAPI
```

Линтер настроен не по принципу «включить всё»: набор правил собран под ошибки,
которые в Go стоят дороже всего (необработанные `err`, утечки ресурсов,
потерянный `context`), под требования безопасности из анализа и под единый
стиль в команде. Обоснование — в комментариях [`.golangci.yaml`](.golangci.yaml).

CI на каждый pull request прогоняет линтер и тесты (MNT3).

## Границы MVP

**Входит:** прохождение за обе роли, ветвление, обучающая обратная связь и
итоговый разбор, балльная оценка и уровень безопасности, история попыток и
динамика, набор из пяти сценариев как данные.

**Не входит, осознанно:**

- Реальная интеграция с чатами и объявлениями классифайда.
- Админ-панель для редактирования сценариев: контент поставляется
  версионируемыми JSON-файлами и загружается при инициализации БД.
- Генерация разбора через LLM. Разбор детерминированный: он воспроизводим, не
  зависит от внешнего сервиса и не может отказать во время демонстрации.
- Мультиязычность, мобильные приложения, офлайн-режим.
- Асинхронные механики: очереди, фоновые задачи, вебсокеты.
- Ролевая модель администраторов.

## Ключевые решения

| Решение | Почему |
|---|---|
| Ветвление, а не линейный опрос | Требование кейса «показывать последствия выбора»: последствие должно менять ход диалога, иначе это викторина |
| Ровно три варианта на шаге: безопасный, спорный, опасный | Компонент диалога пишется один раз под фиксированную сетку, шкала баллов становится единой для всего контента |
| Шкала `+10 / 0 / −10` | Исключает несопоставимость оценок между сценариями и делает пороги уровней универсальными |
| Нормировка от числа сделанных выборов | При ветвлении «лучший путь» неоднозначен; выбранный подход не зависит от структуры графа |
| Порог «внимателен» — 60%, а не 50% | При 50% пользователь, только затягивавший диалог, попадал бы во «внимателен». Это неверное сообщение |
| Сценарии — данные, а не код | Контент пишется параллельно движку, добавление сценария не требует релиза |
| Версионирование сценариев | Правка контента не меняет результатов уже завершённых сессий |
| Регистрация по нику и паролю | Прогресс между попытками требует устойчивой личности; полноценный OAuth для MVP избыточен |
| Гостевой доступ к витрине и справочнику | Продукт виден до регистрации, но прогресс требует учётной записи |
| Разбор без LLM | Воспроизводимость и отсутствие внешних зависимостей на демонстрации |
| Четыре экрана | Прогресс встроен в главную, история — в экран результата: минимум роутов при одном фронтенд-разработчике |

Полные формулировки и альтернативы — в [`Сase-analysis.md`](Сase-analysis.md).
